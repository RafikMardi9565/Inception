# 1.1 — Virtualization vs Containerization

This is one of the most frequently asked evaluation questions.
You must be able to explain both concepts, their differences, and their trade-offs.

---

## 1. Traditional Deployment (the "bare metal" era)

**Before** VMs or containers, you ran one application per physical server.

| Problem | Consequence |
|---------|-------------|
| One app per machine | Massive hardware waste; each server sat at ~10% CPU |
| Dependency hell | Two apps needing different library versions couldn't coexist |
| Slow deployment | Provisioning a new server took weeks |
| No isolation | A crashing app could bring down the whole system |

**Solution needed:** Run multiple isolated environments on the same physical machine.

---

## 2. Virtualization (Hypervisor / Virtual Machines)

### What it is
A **hypervisor** (a piece of software) sits directly on the hardware (Type 1, e.g. VMware ESXi, KVM) or on a host OS (Type 2, e.g. VirtualBox, VMware Workstation). It creates **Virtual Machines** — each one is a complete emulation of a physical computer with its own:

- **Guest operating system** (its own kernel — e.g. a full Linux or Windows kernel)
- Virtualized CPU, RAM, disk, network interfaces
- Its own set of processes, users, and drivers

### How it works, step by step
1. The hypervisor partitions the physical hardware resources.
2. When you create a VM, the hypervisor allocates a slice of CPU cores, RAM, and disk.
3. A full OS image boots inside that VM — it goes through the entire boot process (BIOS/UEFI → bootloader → kernel → init system).
4. The guest kernel talks to emulated/virtual hardware devices exposed by the hypervisor.
5. The guest kernel has **no idea** it's sharing physical hardware with other VMs.

### Architecture diagram (logical)

```
┌──────────────────────────────────────────────────────┐
│                    PHYSICAL HARDWARE                   │
│  CPU | RAM | Disk | NIC                                │
├──────────────────────────────────────────────────────┤
│                    HYPERVISOR                          │
│  (VMware / KVM / VirtualBox / Hyper-V)                 │
├─────────────────┬─────────────────┬──────────────────┤
│     VM 1         │      VM 2       │      VM 3        │
│  ┌─────────────┐ │ ┌─────────────┐ │ ┌─────────────┐  │
│  │   App A     │ │ │   App B     │ │ │   App C     │  │
│  │─────────────│ │ │─────────────│ │ │─────────────│  │
│  │   Binaries  │ │ │   Binaries  │ │ │   Binaries  │  │
│  │─────────────│ │ │─────────────│ │ │─────────────│  │
│  │ GUEST OS    │ │ │ GUEST OS    │ │ │ GUEST OS    │  │
│  │ (kernel)    │ │ │ (kernel)    │ │ │ (kernel)    │  │
│  └─────────────┘ │ └─────────────┘ │ └─────────────┘  │
└─────────────────┴─────────────────┴──────────────────┘
```

### Pros of VMs
- **Strong isolation:** Each VM has its own kernel; a kernel panic in VM1 cannot crash VM2.
- **Full OS:** You can run different OS families (Windows on Linux host, etc.).
- **Mature ecosystem:** Snapshots, live migration, vMotion, well-understood security boundaries.
- **Hardware-level security:** Even if an attacker escapes a process, they land inside a separate kernel — a much harder barrier.

### Cons of VMs
- **Heavy:** Each VM carries an entire OS (~1-4 GB of RAM just for the kernel and system services, ~10 GB+ of disk).
- **Slow boot:** A VM takes 30 seconds to 2 minutes to start.
- **Resource waste:** Every kernel, every init system, every `cron` — duplicated across VMs.
- **Limited density:** A host can run maybe 10-50 VMs before running out of RAM.
- **Slow startup/shutdown:** Booting a full OS is slow.

## 3. Containerization (Docker / containerd / Podman)

### What it is
Containers share the **host operating system's kernel**. There is no guest OS and no hypervisor. Instead, the Linux kernel provides native isolation primitives that Docker orchestrates:

| Kernel feature | What it isolates |
|----------------|------------------|
| **PID namespace** | Each container sees only its own processes (PID 1 inside the container != PID 1 on the host) |
| **NET namespace** | Each container gets its own network stack (interfaces, routing table, iptables rules) |
| **MNT namespace** | Each container has its own filesystem mount points |
| **UTS namespace** | Each container can have its own hostname |
| **IPC namespace** | Inter-process communication is isolated |
| **USER namespace** | Root in a container is a regular user on the host (opt-in) |
| **cgroups** | Limits how much CPU, RAM, I/O a container can consume |
| **UnionFS (OverlayFS)** | Layers that make images efficient — only changed files are stored in new layers |

### How it works, step by step
1. Docker reads a Dockerfile — a list of instructions (FROM, RUN, COPY…).
2. Each instruction creates a **layer** (a diff applied on top of previous layers). These layers are stored using OverlayFS or a similar union filesystem.
3. The final result is an **image** — a read-only stack of layers.
4. When you `docker run`, Docker creates a thin writable layer on top, sets up namespaces + cgroups, and starts the process defined by `CMD` / `ENTRYPOINT`.
5. That process becomes **PID 1** inside the container. It sees only itself and its children. It has no access to host processes, host network interfaces (unless explicitly granted), or host files (unless a volume is mounted).
6. The container does **not** boot. No init system. No kernel. It starts the app directly in ~milliseconds.

### Architecture diagram (logical)

```
┌──────────────────────────────────────────────────────┐
│                    PHYSICAL HARDWARE                   │
│  CPU | RAM | Disk | NIC                                │
├──────────────────────────────────────────────────────┤
│                    HOST OS (Linux)                     │
│                    (single kernel)                     │
├──────────────────────────────────────────────────────┤
│                   DOCKER ENGINE                        │
│  (orchestrates namespaces, cgroups, images, networks)  │
├─────────────────┬─────────────────┬──────────────────┤
│  Container 1     │  Container 2     │  Container 3      │
│  ┌─────────────┐ │ ┌─────────────┐ │ ┌─────────────┐   │
│  │   App A     │ │ │   App B     │ │ │   App C     │   │
│  │─────────────│ │ │─────────────│ │ │─────────────│   │
│  │   Bins/Libs │ │ │   Bins/Libs │ │ │   Bins/Libs │   │
│  └─────────────┘ │ └─────────────┘ │ └─────────────┘   │
│      (no OS)     │     (no OS)     │     (no OS)        │
└─────────────────┴─────────────────┴──────────────────┘
```

### Pros of Containers
- **Lightweight:** No guest OS — only the application and its dependencies. Disk footprint: tens of MB instead of GBs.
- **Fast:** Starts in under a second (just fork a process, set up namespaces, done).
- **High density:** A host can run hundreds or thousands of containers.
- **Reproducible:** The image is a snapshot of the entire runtime environment. "It works on my machine" dies.
- **Layered builds:** Images are built from layers; unchanged layers are cached. Rebuilds are fast.
- **Dev/prod parity:** The same image runs on your laptop, in CI, and on production.

### Cons of Containers
- **Weaker isolation:** All containers share the same kernel. A kernel exploit in one container compromises the host.
- **Linux-only kernel:** Windows containers exist but are inherently less mature. You can't run a real Windows kernel in a container on Linux.
- **State is harder:** Containers are designed to be ephemeral. Persisting state requires volumes and careful design.
- **Networking is complex:** Overlay networks, iptables rules, NAT — debugging container networking is non-trivial.

### Related Concepts and History

**chroot (1979):** The ancestor of all containerization. `chroot(2)` changes the apparent
root directory of a process. It isolates **only the filesystem** — and weakly: no process
isolation, no network isolation, no resource limits, and root can escape it (chroot does
not drop privileges; with mknod/mount tricks a root process can break out).

A container ≈ chroot + namespaces + cgroups + capabilities.

**The evolution:**
- BSD jails (2000), Solaris Zones (2004), OpenVZ (2005) — OS-level virtualization with kernel support
- **LXC** (2008) — "Linux Containers", the first mainstream Linux solution. Docker's
  earliest versions used LXC as their default execution driver before replacing it with
  their own **libcontainer** (direct syscalls), which later evolved into **runc**

**OCI (Open Container Initiative, 2015):** A Linux Foundation project that standardized
- The **image spec** (how an image is structured: layers, manifest, config)
- The **runtime spec** (how a runtime must launch a container: the JSON config runc consumes)

runc is the reference implementation. Thanks to OCI, an image built by Docker runs on
Podman, containerd, CRI-O, or Kubernetes — that is what "portable" really means.

**Docker Desktop and the hidden VM:** Containers need the host's Linux kernel. On macOS
and Windows, Docker Desktop therefore runs a **hidden Linux VM** (HyperKit / Apple
Virtualization framework on Mac; WSL2 or Hyper-V on Windows) and runs all containers
inside it. Inception makes the same architecture explicit: a real Linux VM, with Docker
installed inside it.

## 4. Side-by-Side Comparison

| | Virtual Machine | Container |
|---|-----------------|-----------|
| **Isolation unit** | Entire virtual computer | A single process tree + namespaces |
| **Boot time** | 30s – 2 min | < 1 second |
| **RAM overhead** | 1-4 GB per VM | A few MB per container |
| **Disk per instance** | 10 GB+ each | Hundreds of MB total (shared layers) |
| **Has its own kernel?** | Yes (full guest kernel) | No (shares host kernel) |
| **Can run different OS?** | Yes (Windows on Linux, etc.) | No (must be same kernel as host) |
| **Security boundary** | Very strong (separate kernel) | Good, but weaker than VMs |
| **Performance** | Near-native (with PV drivers) | Native (no emulation) |
| **Portability** | Medium (hypervisor-dependent VMDK/VHD) | High (OCI image standard) |
| **Who manages isolation?** | Hypervisor | Linux kernel (namespaces + cgroups) + Docker Engine |
| **Typical use** | Run apps needing full OS; multi-tenant hosting | Microservices, CI/CD, stateless apps, dev envs |

## 5. Analogy

| Concept | Analogy |
|---------|---------|
| **Physical server** | An apartment building |
| **Virtual Machine** | A condominium — each owner has their own walls, floors, plumbing (kernel), and front door. You can do whatever you want inside; your neighbor's fire won't spread to you. |
| **Container** | A room in a shared house — you share the kitchen and bathroom (kernel) with others. Faster to move in, but your roommate flooding the bathroom affects everyone. |

## 6. Why Docker Chose This Model (and why Inception uses it)

- **Density for microservices:** A VM per microservice would be absurdly wasteful; containers make it practical.
- **Immutable infrastructure:** Build once, run anywhere. The image is the artifact — no "server drift".
- **DevOps velocity:** Spin up a full stack (database + backend + frontend) in seconds on a developer's laptop.

For the **Inception project**, containers are the natural fit:
- You need 3+ services; putting each in its own container is clean and lightweight.
- Running 3 full VMs for NGINX, WordPress, and MariaDB would be absurd (and impossible on a single laptop VM).
- Docker Compose lets you define and run the entire stack with one command.

---

## 7. Key Points to Memorize for Evaluation

1. **VM = virtual hardware + guest kernel.** Container = process isolation at the OS level, sharing the host kernel.
2. The host kernel provides the isolation via **namespaces** (process, network, mount, user, etc.) and **cgroups** (resource limits).
3. VMs are **heavier** but **more secure**; containers are **lightweight** but share the same kernel.
4. Docker does not emulate hardware; it uses the Linux kernel's native features.
5. Inception must run in a **VM** (the project VM), and inside that VM, Docker runs the **containers** — so you have both: VM for isolation of the whole project, containers for the individual services.

## 8. Check Your Understanding

> Answer these without looking:

- Why can you run 100 containers but only 5 VMs on the same hardware?
- What kernel feature isolates the list of processes visible inside a container?
- If a container runs as `root`, is it root on the host? (Default: yes — same UID 0 on the host, but with a reduced capability set. Only with the opt-in USER namespace is it mapped to an unprivileged host UID.)
- Can containers on a Linux host run a Windows application? Why / why not?
- How long does it take to "boot" a container? Why?
- What does chroot isolate, and what is it missing compared to a container?
- What does the OCI standardize, and why does it matter?
