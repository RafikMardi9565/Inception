# MariaDB — Understanding Walkthrough

## 1. What MariaDB Is

MySQL is a database: software that stores data in tables and answers SQL. In 2008–2009, the company behind it got bought by Oracle (MySQL AB → Sun → Oracle). The original developers worried Oracle would make it less open — so they copied the source code and continued it as **MariaDB**. Same DNA, independent project.

For Inception, they're **interchangeable**: same SQL, same port 3306, same client tools (`mysql`, `mysqldump`), same protocol — WordPress can't tell the difference. The subject demands MariaDB.

## 2. Architecture: One Process, Many Threads

When the container starts there is exactly **one process**: `mysqld` (PID 1). Inside it, threads:

- **connection thread** — listens on port 3306, accepts incoming connections
- **worker threads** — one per connected client, executing its queries
- **I/O thread** — flushes dirty pages from memory to disk, in the background
- **purge thread** — cleans up old row versions (garbage collection), in the background

All share one PID and one memory space. Contrast for eval: **nginx is multi-process** (master + worker processes), **mysqld is multi-threaded** (one process, many threads).

**The worker executes queries itself.** It parses the SQL, finds/modifies data in memory, builds the result. The I/O and purge threads are background janitors — the worker doesn't send them work or wait for them:

- I/O thread = writes memory to disk lazily (worker never blocks on disk).
- Purge thread = deletes garbage old row versions lazily (other transactions may still need them).

**One process answers all clients:** connection thread accepts a new client → spawns a dedicated thread → that thread runs the client's queries → client disconnects → thread dies. 50 clients = 1 process with ~50 worker threads. (Default limit ~151 connections.)

## 3. Config: bind-address and Why Docker Breaks the Default

By default MariaDB listens only on `127.0.0.1` (loopback) — "accept connections only from this same machine."

Docker breaks that assumption: **WordPress is a different machine.** Each container has its own network namespace, so WordPress's `127.0.0.1` points to itself, not to MariaDB. From WordPress's world, MariaDB is a remote machine on the Docker network.

Fix:

```ini
[mysqld]
bind-address = 0.0.0.0
port = 3306
```

`0.0.0.0` = "listen on **all** interfaces", including the Docker bridge — MariaDB answers at `mariadb:3306` for any container on the network. Without it: the most common MariaDB failure in Inception (WordPress's connection hangs and dies).

## 4. How WordPress Talks to MariaDB

WordPress is PHP code. On every page load it:

1. **Connects** — opens a TCP connection to `mariadb:3306` using credentials from `wp-config.php`.
2. **Queries** — sends SQL (`SELECT post_title FROM wp_posts WHERE ...`).
3. **Fetches** — gets rows back and renders them into HTML.

Key points:

- Every page view = 20–40 queries (post, metadata, theme, menu, settings...).
- The DB is the **stateful layer** — wipe the volume and the whole site is empty even though the code is untouched.
- `wp-config.php` holds `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` — these must **exactly match** what the MariaDB entrypoint created, or "Access denied".

**The layers:** MariaDB stores raw content (text in tables) — never HTML. PHP is the middleman: reads content from the DB and assembles the HTML page. HTML/CSS/JS is the finished product generated by PHP. Editing a post = PHP sends `UPDATE`; viewing = PHP sends `SELECT`.

**The full chain:** Browser → nginx (443) → php-fpm (9000) → MariaDB (3306), answer travels back up the same road.

- nginx is a dumb door: static files (CSS/JS/images) served directly from disk; PHP requests forwarded to php-fpm.
- **WordPress itself IS written in PHP** — that's why php-fpm exists. A JavaScript backend (Node) would need a Node runtime instead of php-fpm; this stack runs server-side PHP only. (JS *in the browser* is fine — it's static files.)

## 5. First Boot: Initializing the Database

Everything MariaDB knows lives in `/var/lib/mysql` — tables, users, passwords, content. That directory sits on the **volume**.

- **Very first start** — volume empty, no system tables → mysqld cannot even boot.
- **After that** — volume holds everything; container death doesn't matter, new container mounts the same volume.

The entrypoint's real job: **detect the difference** between "brand-new empty database" and "returning database". Everything in this step is the answer to "brand-new".

### 5.1 The system tables: mariadb-install-db

```sh
mariadb-install-db --user=mysql --datadir=/var/lib/mysql
```

Builds the **`mysql` database** — the internal system database with bookkeeping tables:

| Table | What it tracks |
|---|---|
| `user` | Who can log in (users, passwords, hosts) |
| `db` | What each user can access per database |
| `tables_priv` | Table-level permissions |

Two kinds of databases: the `mysql` **system** DB (MariaDB's own memory, built once) and the `wordpress` **app** DB (your content, created by you). Without system tables, mysqld exits with an error.

### 5.2 Why mysqld refuses to run as root

Security by design: a database server parses untrusted network input. Running as OS root means any bug = attacker owns the whole machine. So mysqld hard-refuses to run as root (unless forced with `--user=root`) and instead runs as the low-privilege `mysql` OS user.

Inside the container it's the same mechanism as a normal Linux server: the process starts as root, does its privileged setup, then **drops itself to the `mysql` user** before serving clients. The container doesn't demote anything — mysqld demotes itself. (The container-as-a-whole still runs as root on the host — separate USER-namespace topic.)

### 5.3 Creating the WordPress database

```sql
CREATE DATABASE IF NOT EXISTS wordpress;
```

One database = one named container of tables. Separate DB because: isolation (compromise stops at `wordpress.*`), clean permissions ("wpuser may use wordpress and nothing else"), convention (the `mysql` DB is MariaDB's private property). `IF NOT EXISTS` = idempotency habit.

### 5.4 Creating the WordPress user

```sql
CREATE USER IF NOT EXISTS 'wpuser'@'%' IDENTIFIED BY 'password_from_secret';
GRANT ALL PRIVILEGES ON wordpress.* TO 'wpuser'@'%';
FLUSH PRIVILEGES;
```

- `CREATE USER` — account with name + password (password comes from `/run/secrets`, never plain text).
- `GRANT ... ON wordpress.*` — everything *inside the wordpress database only*.
- `FLUSH PRIVILEGES` — reload permission tables so changes apply without restart.

## 6. The Auth Model: user@host

MariaDB accounts have two halves, both must match:

```
'wpuser'@'%'
  └┬┘    └┬┘
  who   from where
```

`%` is a wildcard = **any host**. Why not pin WordPress's IP? Container IPs change on every restart — hardcode `172.18.0.3` and tomorrow WordPress is `172.18.0.5` → denied → site down.

**One special case:** connections that resolve to `localhost` — the unix socket, or TCP from `127.0.0.1` which MariaDB reverse-resolves — are matched against `'user'@'localhost'` rows, **never** against `'user'@'%'`. That's fine for WordPress (the docker-network IPs don't reverse-resolve, so `%` applies), but it's why `mariadb -u wpuser` *from inside the mariadb container* fails with `Access denied for 'wpuser'@'localhost'` — that connection isn't "remote" in MariaDB's eyes. Inspect with root there, or the same credentials from another container.

**Can't use `'wpuser'@'wordpress'` either:** MariaDB matches the **source IP** of the connection, not a client-reported name. Docker's embedded DNS only does forward resolution (name → IP); there's no reverse resolution (IP → name) in the container network. The MySQL wire protocol carries no "my name is wordpress" — the server sees only an IP. So `%` is the correct call.

Other host values: `'localhost'` (local socket only), `'192.168.%'` (subnet), `'172.18.0.3'` (exact IP).

## 7. The Debian Root-Auth Gotcha (unix_socket)

On Debian, MariaDB's `root` account ships **without a password**, secured by the `unix_socket` plugin:

- `mysql -u root` works **only** as OS root, through the local socket.
- From anywhere else: denied — there is no password to enter.

The trap: running `ALTER USER 'root'@'localhost' IDENTIFIED BY '...'` switches root from socket auth to **password auth** — bare `mysql -u root` (no `-p`) stops working. Healthchecks that do `mysqladmin ping -u root` then mysteriously fail.

**The rule: be consistent.** Either:

1. **Keep socket auth** — don't touch root; only create password-authenticated app users.
2. **Set the root password** — then always use `-p` in every script/healthcheck that connects as root.

Whatever you choose, it must behave the way you claim at eval.

## 8. The wp_ Tables — What WordPress Will Create

WordPress manages its own database structure. After wp-cli installs WordPress, your `wordpress` database contains these tables (all prefixed `wp_`):

| Table | Content |
|---|---|
| `wp_posts` | Blog posts, pages, custom post types |
| `wp_postmeta` | Extra metadata for posts (custom fields) |
| `wp_users` | User accounts (login, email, hashed password) |
| `wp_usermeta` | User profile fields, capabilities |
| `wp_comments` | Post comments |
| `wp_commentmeta` | Comment metadata |
| `wp_terms` | Categories and tags |
| `wp_term_taxonomy` | Category/tag type definitions |
| `wp_term_relationships` | Which posts belong to which categories/tags |
| `wp_options` | Site-wide settings (site URL, theme, plugins) |
| `wp_links` | Blogroll links (mostly legacy) |

Key point: **WordPress creates these itself.** Your entrypoint's job ends at creating an empty `wordpress` database + user. The tables appear when wp-cli runs the WordPress install (in the WordPress container, which connects using the credentials you set up here).

The eval command — the evaluator will run this to see your tables:

```bash
docker exec -it mariadb mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" -e "SHOW TABLES;"
```

## 9. Ports Summary — Why Only 443 Is Open

```
Browser → NGINX (443, HTTPS/TLS) → WordPress/php-fpm (9000, FastCGI) → MariaDB (3306, MySQL protocol)
```

| Source | Target | Port | Protocol | Data |
|---|---|---|---|---|
| Browser | NGINX | 443 | HTTPS (TLS 1.2/1.3) | Web pages |
| NGINX | WordPress/php-fpm | 9000 | FastCGI over TCP | PHP execution requests |
| WordPress | MariaDB | 3306 | MySQL wire protocol | SQL queries |

**Port 443 is the ONLY port published to the host.** Ports 9000 and 3306 exist only on the internal Docker bridge network — outside the VM they are unreachable. This is by design:

- One door in, everything else is internal — minimal attack surface.
- An attacker on the host (or outside the VM) cannot talk to MariaDB or php-fpm directly; they must go through nginx, TLS, and WordPress.
- Compose does this: nginx gets `ports: "443:443"`; WordPress and MariaDB get **no** `ports:` — they're reachable only by their DNS names (`wordpress:9000`, `mariadb:3306`) from containers on the same network.

## C.5 requirements/mariadb/Dockerfile

```dockerfile
# **************************************************************************** #
#    MARIADB                                                                   #
# **************************************************************************** #

# ---------- BASE IMAGE ----------
FROM debian:bookworm

# ---------- CONFIGURATION ----------
RUN apt-get update && apt-get install -y mariadb-server \
    && rm -rf /var/lib/mysql/*

# ---------- CONFIG FILE ----------
COPY conf/50-server.cnf /etc/mysql/mariadb.conf.d/50-server.cnf

# ---------- TOOLS ----------
COPY tools/entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

# ---------- ENTRYPOINT ----------
ENTRYPOINT ["/entrypoint.sh"]
```

Notes:
- No `EXPOSE`, no `CMD` — by your choice (documentation-only, and the script hardcodes `mysqld`).
- `COPY conf/...` **overwrites** Debian's stock `50-server.cnf` (which has `bind-address = 127.0.0.1`) with yours.
- **`rm -rf /var/lib/mysql/*` — THE copy-up trap killer.** `apt-get install mariadb-server` bakes a virgin datadir into the image. Docker's volume initialization copies image content into an *empty named volume* on first mount — so the fresh volume would arrive pre-seeded with `mysql/` system tables, the entrypoint's `[ ! -d /var/lib/mysql/mysql ]` would think init already happened, skip user/DB creation, and WordPress would die with error 1130. Shipping an empty datadir in the image means copy-up copies nothing, and the entrypoint's freshness check works. (This is also why the official mariadb image ships an empty datadir.)

## C.6 requirements/mariadb/tools/entrypoint.sh

```sh
#!/bin/sh
set -e

mkdir -p /run/mysqld
chown mysql:mysql /run/mysqld

if [ ! -d /var/lib/mysql/mysql ]; then

	mariadb-install-db --user=mysql --datadir=/var/lib/mysql

	mysqld --user=mysql --skip-networking &
	pid=$!

	for i in $(seq 1 30); do
		if mariadb-admin ping --silent; then
			break
		fi
		sleep 1
	done

	MYSQL_PASSWORD=$(cat /run/secrets/db_password)
	MYSQL_ROOT_PASSWORD=$(cat /run/secrets/db_root_password)

	mariadb -u root <<SQL
CREATE DATABASE IF NOT EXISTS \`${MYSQL_DATABASE}\`;
CREATE USER IF NOT EXISTS '${MYSQL_USER}'@'%' IDENTIFIED BY '${MYSQL_PASSWORD}';
GRANT ALL PRIVILEGES ON \`${MYSQL_DATABASE}\`.* TO '${MYSQL_USER}'@'%';
ALTER USER 'root'@'localhost' IDENTIFIED BY '${MYSQL_ROOT_PASSWORD}';
FLUSH PRIVILEGES;
SQL

	mariadb-admin -u root -p"${MYSQL_ROOT_PASSWORD}" shutdown
	wait $pid || true
fi

exec mysqld --user=mysql
```

Line by line:

- `set -e` — exit on first failure.
- `mkdir /run/mysqld` + `chown` — the socket directory. Debian's package usually creates it via its init script; in a container, we make it ourselves. **It must be created on EVERY boot — outside the `if`** — because the final `mysqld` needs it even when init is skipped.
- `if [ ! -d /var/lib/mysql/mysql ]` — the **idempotency check** (step 5). The `mysql` system database exists only after initialization. Volume fresh → init. Volume populated → skip straight to `exec`. **This check silently breaks if the image ships a datadir** — Docker's copy-up would seed `mysql/` into a fresh volume and the check would wrongly skip init (the `rm -rf /var/lib/mysql/*` in the Dockerfile is what keeps this honest).
- `mariadb-install-db --user=mysql` — builds the system tables (step 5.1). Must run as the `mysql` user.
- `mysqld --user=mysql --skip-networking &` — start a temporary instance (background) just for the setup SQL. `--skip-networking` keeps it local-only during init. `--user=mysql` avoids the "refuses to run as root" refusal (step 5.2).
- The `for` loop — wait up to 30s for the socket to appear, pinging every second.
- `$(cat /run/secrets/db_password)` — read the secret file, never hardcode.
- The `mariadb -u root <<SQL` heredoc — connects as OS root via unix_socket (still works here, root has no password *yet*) and runs the setup (steps 5.3, 5.4, 7):
  - create the `wordpress` database
  - create `wpuser` with `%` host (step 6)
  - `ALTER USER root ... IDENTIFIED BY` — switches root from socket auth to **password auth** (step 7). After this, every root connection needs `-p`.
- `mariadb-admin -u root -p"..." shutdown` — clean shutdown of the temp instance. Note the `-p`: root now has a password.
- `wait $pid || true` — reap the temp mysqld (shutdown kills it; `|| true` so `set -e` doesn't trip on the non-zero exit).
- `exec mysqld --user=mysql` — replace the script with the real server, foreground, PID 1. **No `daemon off`-style flag needed — mysqld doesn't daemonize when launched directly.**

## C.8 srcs/docker-compose.yml

```yaml
services:
  mariadb:
    build:
      context: ./requirements/mariadb
    container_name: mariadb
    restart: always
    environment:
      MYSQL_DATABASE: ${MYSQL_DATABASE}
      MYSQL_USER: ${MYSQL_USER}
    secrets:
      - db_password
      - db_root_password
    volumes:
      - mariadb_data:/var/lib/mysql
    networks:
      - inception_net

secrets:
  db_password:
    file: ../secrets/db_password.txt
  db_root_password:
    file: ../secrets/db_root_password.txt

volumes:
  mariadb_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /home/rmardi/data/mariadb

networks:
  inception_net:
```

Notes:

- `secrets: file:` — compose v2 feature (no swarm needed); mounts the file read-only at `/run/secrets/db_password` inside the container.
- **Paths are relative to the compose file**: compose lives in `srcs/`, secrets in `../secrets/`.
- `volumes: mariadb_data:/var/lib/mysql` — the stateful layer. Data survives `docker compose down`.
- **Subject rule — named volume in `/home/rmardi/data`:** bind mounts are forbidden for these volumes; the subject demands named volumes whose data lives in `/home/rmardi/data` on the host. This block satisfies both: `mariadb_data` is declared by name in the top-level `volumes:` section (it shows up in `docker volume ls`), and the `local` driver's `device:` option puts the data in the real host directory. No `- /host:/path` bind syntax under any service. The Makefile creates `/home/rmardi/data/mariadb` before `up`.
- **No `ports:`** — by design (step 9). MariaDB is reachable only from other containers on `inception_net`, at `mariadb:3306`.
- `restart: always` — subject requirement; DB auto-recovers from crashes.
- `environment:` — only the non-secret names; passwords enter via secrets only.

## C.9 Build, run, test

```bash
cd srcs
docker compose up -d --build mariadb
```

Then verify, in order:

```bash
# 1. It's running?
docker compose ps

# 2. Logs (init happened?)
docker compose logs mariadb

# 3. Log in as root (password from db_root_password.txt)
docker exec -it mariadb mariadb -u root -p

# 4. Inside the shell:
SHOW DATABASES;          -- expect: information_schema, mysql, performance_schema, sys, wordpress
SELECT user, host FROM mysql.user;   -- expect: root, wpuser ('%')
exit
```

**What you'll see in `mysql.user` — and why it's normal:** besides `root`, `mysql`, `mariadb.sys` and your `wpuser`, Debian's bootstrap adds a `test` database, **anonymous users** (`''@localhost` and `''@<hostname>` — in a container the hostname IS the container ID, e.g. `''@7ba2da57b42c`) and a `PUBLIC` role row (MariaDB 10.11+). Not corruption — standard Debian/MariaDB bootstrap artifacts. Harmless for Inception; `mysql_secure_installation` would remove them if you ever wanted hardening.

**Persistence test** (the volume in action):

```bash
docker compose down
docker compose up -d mariadb
# logs should NOT show re-initialization — data survived
```

Note: `SHOW TABLES` in `wordpress` will be **empty** — the `wp_` tables appear only after WordPress (wp-cli) installs itself. That's expected.

## C.10 Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `mysqld: Please read "Security" section... run as root` | forgot `--user=mysql` | add `--user=mysql` to every mysqld invocation |
| WordPress later: `Connection refused` / hang | `bind-address` still 127.0.0.1 | check the conf COPY overwrote `/etc/mysql/mariadb.conf.d/50-server.cnf` |
| `Access denied for user 'wpuser'` | secret value mismatch with wp-config later | passwords must match across entrypoint + WordPress config |
| `mariadb-admin ping` hangs in loop | missing socket dir | `mkdir -p /run/mysqld && chown mysql:mysql` |
| `Can't start server : Bind on unix socket` on second boot | socket dir created only inside the `if` (init skipped on reboot) | `mkdir -p /run/mysqld` must run on EVERY start — put it before the `if` |
| `secret db_password is declared in external file` error | wrong relative path | from `srcs/` it must be `../secrets/db_password.txt` |
| Re-init on every `up` | volume not mounted or check wrong | confirm `volumes: mariadb_data:/var/lib/mysql` |
| `mariadb -u root` suddenly asks for password | expected after ALTER USER | always use `-p` after first init — that's step 7 in action |

**First boot vs second boot:**

| | First boot (empty volume) | Second boot (data present) |
|---|---|---|
| socket dir | created | created (moved OUTSIDE the `if` after the bug!) |
| system-db check | missing → init | exists → skip everything |
| temp server + SQL | runs (create DB/user, set root pw) | skipped |
| final `exec mysqld` | runs | runs — the whole difference |

**The three "somethings":**

| Thing | What it is | Where it lives | When it exists |
|---|---|---|---|
| **Server** (mysqld) | the running program, PID 1 | baked in the image | from first boot |
| **Structure** (system tables) | MariaDB's own bookkeeping | the volume (`mysql` DB) | created by `mariadb-install-db` once |
| **Content** (wordpress DB) | shell created by us; `wp_` tables by WordPress later | the volume | DB shell at first boot; tables when wp-cli installs WordPress |

**One chain, three containers:**

```
  nginx        wordpress        mariadb
 (the door)    (the engine)    (the memory)
   :443    →     :9000     →      :3306
  HTTPS        FastCGI           MySQL
```
