# WordPress — Questions

## What WordPress IS

1. "WordPress is not a program that runs." What does that mean?

> **Answer:** WordPress is PHP CODE — files sitting on the volume. Nothing named "wordpress" runs as a process. The PROCESS is php-fpm (PID 1 of the wordpress container): it reads index.php, interprets it, executes it. Between requests, nothing "wordpress" exists. Analogy: WordPress = recipe book, php-fpm = chef, MariaDB = pantry.

2. Where do the three parts of the "working website" live?

> **Answer:** Engine (php-fpm) — baked in the image. Code (index.php, themes, plugins) — on the wordpress volume (`/home/rmardi/data/wordpress`). Content (posts, users, settings) — rows in MariaDB. Three containers, three layers: door (nginx), engine+code (wordpress), memory (mariadb).

3. Is a PHP file like a .py script? Explain with the interpreter analogy.

> **Answer:** Yes — a .php file is inert text until a PHP interpreter executes it. php-fpm's worker = the interpreter for web requests; php-cli = the interpreter for the command line. Same language, two engines. WordPress without PHP is just files on disk.

## php-fpm

4. What is php-fpm, and what can it NOT do?

> **Answer:** FastCGI Process Manager — the PHP execution engine. It CANNOT speak HTTP and is not a web server; it speaks FastCGI only. Master process (config, worker lifecycle) + worker processes (each executes ONE PHP script at a time, stateless). In our stack it listens on TCP 9000.

5. Why TCP `0.0.0.0:9000` and not the default unix socket?

> **Answer:** The default `listen = /run/php/php8.2-fpm.sock` is a file — only reachable from the same filesystem (same container). nginx lives in a different container with a different filesystem namespace: the socket file doesn't exist there. TCP is network-reachable; nginx connects to `wordpress:9000` via Docker DNS. Our `www.conf` overwrite is what makes this work — it's not optional.

6. What does `php-fpm -F` do, and why is the `-F` critical?

> **Answer:** `-F` = stay in the foreground (no daemonizing). Without it php-fpm forks to the background, the original PID 1 exits, and the container dies instantly. With it, the master stays PID 1 and the container lives. Note the binary name: `php-fpm8.2` on Debian bookworm.

7. Explain every line of our www.conf and why each is needed:

```ini
[www]
user = www-data
group = www-data
listen = 0.0.0.0:9000
pm = dynamic
pm.max_children = 5
pm.start_servers = 2
pm.min_spare_servers = 1
pm.max_spare_servers = 3
```

> **Answer:** `[www]` = pool name (syntax requirement). `user/group www-data` = workers run as the low-privilege web user (not root; php-fpm refuses root workers anyway). `listen` = TCP 9000, all interfaces — the cross-container line. `pm = dynamic` = worker-pool mode — MANDATORY (no default; without it: "the process manager is missing"). `max_children` = 5 concurrent requests cap (also no default — we learned that the hard way). `start_servers`/`min_spare`/`max_spare` = boot workers + idle spare bounds. "Minimal" means no extra lines, not fewer than required — php-fpm validated that for us twice.

8. Why does the entrypoint end with `chown -R www-data:www-data /var/www/html`?

> **Answer:** wp-cli ran as root, so every downloaded/installed file is root-owned. But the php-fpm WORKERS run as www-data and must write (user uploads, plugin updates). The chown hands the site files to the workers' user. Mismatch = "permission denied" on every write.

## wp-config.php

9. What is wp-config.php and what does it hold?

> **Answer:** The bridge between WordPress and the database: DB_NAME, DB_USER, DB_PASSWORD, DB_HOST — plus eight random security salts (cookie signing) and the table prefix. Generated by `wp config create` (wp-cli) at first boot, written onto the volume.

10. Why is `DB_HOST = mariadb:3306` and not `localhost`?

> **Answer:** From the wordpress container's world, MariaDB is a REMOTE machine on the docker network. `localhost` would mean "inside my own container" (127.0.0.1 — nothing there). `mariadb` is resolved by Docker's embedded DNS to the mariadb container's IP. Every credential must exactly match what the mariadb entrypoint created or it's "Access denied" / "Error establishing a database connection".

## WP-CLI & the Install

11. What is WP-CLI, and why use it instead of the browser install wizard?

> **Answer:** WordPress's command-line admin tool — a single PHP phar file at `/usr/local/bin/wp-cli.phar` (with a `wp` symlink). It automates download/config/install/user-creation, making the whole thing scriptable and idempotent. The evaluator must see a FULLY INSTALLED WordPress at first visit — no "choose your language" wizard. wp-cli makes that deterministic.

12. Why do all `wp` commands carry `--allow-root`?

> **Answer:** wp-cli refuses to run as root (a WordPress codebase has full filesystem power; running it as root is dangerous) unless you explicitly say `--allow-root`. Our containers run as root by design, so every invocation needs it.

13. The four wp-cli commands our entrypoint uses — what does each do?

> **Answer:** `wp core download` — fetch all WordPress files onto the volume. `wp config create` — write wp-config.php with DB credentials + salts. `wp core install` — create the `wp_` tables in MariaDB + the admin user (--url, --title, --admin_user/email/password, --skip-email). `wp user create` — the second user (--role=author).

14. Why did our first build ship a broken `wp` — and what was the `404:: not found` error?

> **Answer:** Two bugs, both classic: (1) the raw.githubusercontent versioned URL now returns 404, and `curl -O` happily saves the 404 HTML page as the "binary" (exit 0!) — the shell then tried to run it and choked on `404:`. Fix: the official GitHub release URL with `curl -LO` (follows redirects). (2) Renaming the phar to `/usr/local/bin/wp` broke its internal template lookups (the phar's alias is `wp-cli.phar`) — `wp config create` died with a mangled double `phar://` path. Fix: keep the filename `wp-cli.phar` + expose `wp` as a symlink.

15. Walk through the three idempotency checks and what each protects.

> **Answer:** (1) `index.php` missing? → `wp core download` (protects: files). (2) `wp-config.php` missing? → `wp config create` (protects: config). (3) `wp core is-installed` fails? → `wp core install` + `wp user create` (protects: the DATABASE state). Three different checks because three things live in three places — files and config on the volume, installation state in MariaDB. Second boot: all three skip → straight to php-fpm in ~1 second.

16. Why does the third check query the database instead of the filesystem?

> **Answer:** Installation state = the wp_ tables in MariaDB. Even if the whole wordpress volume were wiped, the DB would still say "installed" — so the entrypoint repairs the files (download + config) WITHOUT trying to reinstall over existing tables. Each check independently repairs just what's missing.

17. What does the wait loop do, and why does it ping as wpuser instead of root?

> **Answer:** Knocks on `mariadb:3306` once per second, up to 30s, until the database answers — covering the case where mariadb's own init is still running. It pings as wpuser because root is `'root'@'localhost'` — over the network that connection resolves to a different host and gets denied. `'wpuser'@'%'` can cross the network. The ping ALSO confirms the credentials match, which is why the loop only succeeds when mariadb is truly ready.

## Users & the Subject

18. What does the subject require about WordPress users — and how do we satisfy it?

> **Answer:** Two users: one administrator whose username must NOT contain admin/Admin/administrator (bots brute-force those), and one regular user. Ours: `rmardi` (administrator) and `author` (role=author — can write posts, can't touch settings/plugins/themes). Verified: `SELECT user_login FROM wp_users;` → rmardi, author.

19. How would the evaluator verify the two users behave differently?

> **Answer:** Log in at `/wp-admin` as rmardi → full dashboard (plugins, themes, settings). Log in as author → reduced menu, no install/update powers. Both exist in `wp_users` with different roles in `wp_usermeta` (wp_capabilities).

## Volumes & Sharing

20. Why do nginx and wordpress share ONE volume — and why is nginx's mount read-only?

> **Answer:** WordPress WRITES the site files (wp-cli install, user uploads); nginx READS them (serves static files, hands PHP to php-fpm). Same files, two views of the same host directory. nginx mounts `:ro` — defense in depth: even a compromised nginx can't deface the site. WordPress's mount stays read-write.

21. How do you prove the site files are really on the host?

> **Answer:** `ls /home/rmardi/data/wordpress/` → index.php, wp-config.php, wp-content/, themes... plain files visible from the host. That's the subject's "volume contains the WordPress website files in /home/<login>/data" requirement, verified with ls.

## The Whole Flow

22. Trace one WordPress page load end to end — every hop.

> **Answer:** Browser → nginx (443, HTTPS/TLS) → `.php` request → FastCGI over TCP to `wordpress:9000` → php-fpm worker executes index.php → WordPress boots from wp-config.php → connects to `mariadb:3306` as wpuser → 20–40 SQL queries fetch content → PHP renders HTML → FastCGI back to nginx → HTTPS back to browser. Static files (CSS/JS/images) skip php-fpm entirely — nginx serves them straight from the shared volume.

23. First boot vs second boot of the wordpress container — what differs?

> **Answer:** First boot: ping → download (~30-60s) → config create → core install + user create → chown → exec php-fpm. Second boot: ping (instant) → all three checks skip → chown (no-op) → exec php-fpm. ~1 second, zero network, all content intact — the volume + DB remember everything.
